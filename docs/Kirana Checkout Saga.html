1. The four statuses of an order

An order is a small state machine stored in orders.status (enum OrderStatus). It is born CREATED and moves exactly once, to one of three final statuses.

2. One checkout, end to end

The happy path across the five systems involved. Orange bands are database transactions. Outside them the backend borrows a database connection only for single quick reads, and never while it waits on the gateway.

3. The saga in a box

Two kinds of caller drive the same three steps: the shopper's browser, and background jobs that settle orders nobody finished. All of them pass through one rule before they may change an order.

  1. Reconciler (PaymentJobs.reconcile, then CheckoutSaga.reconcile): finds orders still CREATED, older than 1 minute, that have a gateway order. Asks the gateway. Captured payment found: settles to PAID. Otherwise leaves it alone.
  2. Expiry (PaymentJobs.expire, then CheckoutSaga.expire): finds CREATED orders past paymentDueAt. If a gateway order exists, asks the gateway one last time; paid means PAID. Otherwise FAILED, and the stock goes back. If the gateway cannot be reached, it tries again on the next run, so an order is never expired while the answer is unknown.
  3. Release once: close() restocks only when its UPDATE returned 1 row. Ten simultaneous cancels or expiries release the stock once (tested in CheckoutSagaIntegrationTest).

5. Is the saga a single point of failure?

No, the saga itself is not a single point of failure. CheckoutSaga is a stateless class that runs inside every backend instance. The only thing it remembers between steps is the order row, so any instance can continue any order, and a crash in the middle is cleaned up by the reconciler or the expiry job on another instance.

What is a single point of failure: Postgres (one instance holds every order; replicas and failover come in Stage 12). The payment gateway is outside our control, so we contain it: the circuit breaker, the 2 s timeout, and "pay later" keep orders safe while it is down. Redis is not one: when it fails, checkout skips the flash-sale gate and the database decides.

Does it change how much load checkout can take? Compared with Stage 4, a checkout now costs three short transactions (TX1, TX2, TX3) plus one gateway call made outside any transaction, so no database connection waits on the gateway. The flash-sale gate still turns away losers before TX1, the hot stock row is still locked only during TX1, and the bulkhead caps checkouts at 20 at a time per instance so they cannot crowd out browsing. The cost that grew is the extra round trip to the gateway and the second request (verify), not lock time.

Known gap: every instance runs the jobs. The one-owner rule keeps that correct (only one settles each order), but the work is repeated. A distributed lock or SKIP LOCKED in Stage 8 fixes it.
